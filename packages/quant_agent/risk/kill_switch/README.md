# Kill Switch 核心

本模块控制新增订单。全局或账户开关为 ACTIVE 时拒绝下单；状态缺失、数据库读取异常、
状态时间晚于检查时间同样拒绝。激活不会自动清仓或取消已提交订单。已提交订单的精确幂等回执
仍可查询和重放，因为它不会创建新订单。

## 应用装配

`KillSwitchService` 是应用调用边界，`InMemoryKillSwitchRepository` 用于进程内测试。
`SQLiteKillSwitchRepository` 用于本地持久化：所有使用同一数据库文件的实例共享写事务锁。
同一账户若运行多个执行进程，必须连接同一 Kill Switch 数据库，不能各自创建独立开关。
Paper 账户数据库应使用另一个文件；在 Kill Switch 写事务内连接同一 SQLite 文件提交 Paper
账户会产生锁冲突。

初始化 GLOBAL 和所用 ACCOUNT 后，将服务传入 `PaperExecutionService(new_order_gate=...)`。
Paper 服务会核验允许决策属于当前检查，再在闸门持锁期间撮合和提交。
开关激活与下单依照取得锁的顺序串行完成；激活成功返回后，后续新增订单被阻断。
锁超时或数据库故障使操作显式失败，调用方必须处理失败，不能把未成功的激活当成已经停机。

## 恢复与权限

恢复有三个条件：请求者和审批者都是人工 RISK_ADMIN；可信认证适配器核验身份及审批；
审批绑定当前 ACTIVE 状态哈希、修订号和最新事故，并且在取得仓储锁后仍未过期。
审批期间出现新事故会使旧审批失效。已提交恢复请求的完全相同重放返回原转换记录。

`KillSwitchRecoveryAuthorizer.authorize_recovery(request)` 必须根据独立的身份/审批记录验证
整个请求，仅返回严格的 `True` 才会授权。请求中自声明的角色、哈希和时间不能代替认证。
默认未配置适配器时不能恢复。此核心模块不自带用户登录或审批页面，这由后续 API 层实现。

仓储、数据库文件、时钟和认证适配器是可信应用内部接口。不要向 Agent 或不可信脚本
提供直接仓储访问、数据库写权限或任意 Python 执行能力。Agent 工具层应只暴露受控操作，
不得注册恢复开关、修改审批或替换风控状态的工具。

## 幂等、证据和故障

状态命令共用 `(scope, account_id, idempotency_key)`，同键不同内容冲突。
下单闸门按账户和幂等键记录稳定 `operation_hash`，它包含原订单请求哈希、批次和请求 ID，
不包含每次变化的检查时间。`request_hash` 则绑定本次检查，供审计使用。
被阻断的操作重放最初的阻断决策；恢复后若要重新尝试，必须重新生成并验证新的订单请求。
曾经允许但未完成的订单会重新检查当前开关，不能重用旧的允许决策。

每个 scope 有独立事件哈希链；状态变化、事故和幂等结果一起提交。
外部 AuditSink 是权威事件的投影，投影失败不回滚开关；可以通过相同请求重放重试投影。
如果重放者与原事件 actor 不一致，不会把原事件重新归属给重放者。

`activate_from_reconciliation()` 只接受完整、验证过且要求 STOP_NEW_ORDERS 的
`ReconciliationResult`，保留结果哈希、差异原因和触发证据，随后激活对应账户开关。
独立核对引擎保持只读，应用在消费严重核对结果时调用此入口；自动编排接入属于后续 Harness。
